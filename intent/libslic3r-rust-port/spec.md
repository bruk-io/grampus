# Spec: Port libslic3r to Rust with 1:1 functionality

libslic3r at the pin is 605 source files and about 340,000 lines. This spec does not shrink that.
It fixes the things every later piece of work needs to agree on — the oracle, what "the same
output" means, what is in scope, how one ported unit is proven equal, and how "faithful first"
is enforced — and pushes all per-file detail into generated artifacts that a task commits and a
script re-checks. Every count below is reproduced by a committed script (R8), not quoted from a
conversation.

## Requirements

### R1: One command produces the pinned oracle binary, and refuses any other version

`just oracle-fetch` downloads the OrcaSlicer v2.5.2 release build into its own directory outside
`/Applications`, verifies its sha256 against a recorded value, verifies the binary reports
`2.5.2`, and exits non-zero otherwise. The installed `/Applications/OrcaSlicer.app` (2.4.2) and
`BambuStudio.app` are never read by any command in this repository.

### R2: One command runs the oracle, and fails rather than producing nothing

`just oracle-slice <fixture>` runs the pinned oracle with the recorded machine, process and
filament preset paths under `vendor/OrcaSlicer/resources/profiles/BBL/`, from a scratch working
directory, and exits non-zero unless a non-empty `plate_1.gcode` was written. It always passes
`--outputdir` and an explicit `--load-filaments`, and maps the oracle's negative exit codes
(received by the shell modulo 256) to named failures.

### R3: A committed report records the oracle's run-to-run reproducibility per configuration

`port/reports/determinism.md` names each comparison configuration (base FFF; tree support; wipe
tower and multi-filament; fuzzy skin; and any other the port needs), the number of oracle runs
compared, and for each artifact whether the runs were byte-identical with no normalisation, with
the declared normalisation, or not at all. The report is regenerated by a committed command.

### R4: A committed comparator reports which level of sameness two outputs reach

One comparator takes two G-code files and reports the highest level that passes and the first
failing location at the next level up:

- **L0** identical bytes.
- **L1** identical bytes after the declared normalisation.
- **L2** identical token stream (command plus axis words, comments dropped).
- **L3** identical move count and order, numbers within a declared per-axis tolerance, reporting
  max and RMS deviation per axis.
- **L4** identical per-layer and per-role aggregates (move count, extruded length, E delta,
  bounding box, travel distance, layer count).

The declared normalisation is exactly the four line kinds upstream itself strips in
`vendor/OrcaSlicer/tests/fff_print/test_slicing_pipeline_hook.cpp`: `; generated by `,
`; model label id: `, lines containing `printing object, unique label id: `, and lines
containing `slicing_pipeline_plugin`. Nothing else is normalised. The oracle's
`--export-statistics` and `--export-settings` JSON are compared byte for byte with no
normalisation at all.

### R5: A per-stage oracle dumps the pipeline's intermediate state without changing its output

A committed C++ dumper links the vendored `libslic3r` built from the pin, registers a hook with
`Print::set_slicing_pipeline_hook_fn` (`vendor/OrcaSlicer/src/libslic3r/Print.hpp`), and writes
one dump per `SlicingPipelineStepPlugin` seam per object per layer, serialising integer
`coord_t` coordinates and never round-tripping through float. A check proves the dumping build's
exported G-code is identical at L1 to the same build with the hook unregistered.

### R6: A committed report records whether the two oracles agree

`port/reports/oracle-parity.md` records, for the fixture set, whether the locally built
`libslic3r` and the pinned release binary reach L1 against each other, and lists every
difference found. It names the built oracle's exact CMake flags, including `-ffp-contract=off`.

### R7: Every oracle output records what produced it

Each golden file, dump and report carries a header recording: the pinned commit
`f92a7c065c5718b8ef1baac1cd704df2911238f4`; which oracle produced it and its build flags; OS;
architecture; compiler version; the value of `SCALING_FACTOR`; the full preset set; and the
fixture's basename.

### R8: A committed, regenerated manifest is the authority on scope and progress

`port/manifest.tsv` has one row per libslic3r source file at the pin, with columns: path,
subsystem, lines, include-DAG level, in scope or out with a reason, target crate and module,
equality tier, and status. A committed script regenerates it; re-running the script leaves the
file unchanged, and its row count equals the number of libslic3r source files at the pin. Scope
is what the application calls: the include closure over the four entry points
`Model::read_from_file`, `Print::apply`, `Print::process` and `Print::export_gcode`, minus the
named out-of-scope groups (GUI-only mesh, measure and gizmo helpers; parametric CAD; SLA per R9;
arrange and orient; texture baking; post-export statistics; and files no caller in the vendored
tree reaches). No later document restates the file list; it reads the manifest.

### R9: SLA is excluded by file, not by directory

The manifest marks each `SLA/` file in or out individually with its reason. `SLA/IndexedMesh` is
in scope because Z-contouring calls it; the SLA fields carried on the model type are ported as
data only; the hollowing, pad and concave-hull implementations are out.

### R10: The port's slicing surface is the GUI-free sequence, and the plate layer is out of scope

The port exposes the sequence `vendor/OrcaSlicer/tests/fff_print/test_helpers.hpp` uses — build a
model, apply a config, validate, process, export G-code — and nothing from
`src/slic3r/GUI/PartPlate`. Bed shape, exclusion areas, wipe-tower placement and filament maps
reach the port as resolved configuration values (R11). The Bambu-printer flag the oracle derives
from the printer model is set explicitly by the caller, because validation and G-code depend on
it.

### R11: The port's configuration input is the oracle's resolved config, not preset JSON

The port consumes the resolved configuration the oracle writes with `--export-settings`, which is
byte-stable across runs. Preset files, the `inherits` chain and preset-bundle resolution are out
of scope for this intent, so a benchy difference cannot be caused by preset resolution. The two
keys that exist only in the G-code config block, `first_layer_temperature` and
`first_layer_bed_temperature`, are derived by the port at emission time. Resolved configs are
generated with a throwaway data directory so no print-host credential field is ever committed.

### R12: `docs/PORTING.md` states the per-file translation contract

It is committed before any unit is ported and contains: the crate map, which agents may not
invent; a type map; an idiom map; a don't-translate list; a banned-substitution list; and these
rules, each of which this codebase makes load-bearing:

- The two scaling APIs truncate toward zero. Port them as truncating division by the runtime
  scaling global. Adding rounding is banned.
- Mirror `f32` and `f64` exactly where the original uses `float` and `double`. Widening a
  `float` field changes every emitted E value.
- Two rounding modes coexist: ties-away in the G-code formatter and in Clipper2 point
  construction, ties-to-even in Clipper2 intersections. Each site is ported individually.
- Never widen or narrow an error set. A function that cannot fail does not return `Result`; an
  assertion compiled out in the oracle's release build does not become a live panic.
- Format numbers locale-independently; transcribe the G-code formatter's digit counts,
  zero-padding, decimal insertion and trailing-zero stripping verbatim.
- Never reimplement a linked C or C++ library in Rust in this intent (R17).

### R13: `docs/WORKFLOW.md` states the porting workflow, and each unit's pull request shows it was followed

It is committed before any unit is ported and states: the unit of work (one libslic3r source file
plus its header to one Rust module, except the template-heavy and header-only files, which are
hand-designed once, before fan-out); the two phases, where a Phase A draft is not required to
compile and Phase B compiles bottom-up by DAG level with compiler errors as the work queue; the
loop of one implementer, then two adversarial reviewers in separate contexts who see only the
diff, are told to assume it is wrong, and may not implement, then one fixer; the rejection rule
that a workaround needing a paragraph of justification is wrong code; the conflict discipline for
agents sharing a worktree (commit named files only, no `git stash` or `git reset`, no build
commands, no slow commands); and a three-unit trial run, covering one unit of each equality tier,
whose output corrects `docs/PORTING.md` before fan-out. A port unit's pull request records the
two review verdicts.

### R14: Every ported module is greppable, and a script checks it

`just port-status` fails unless: every Rust module that ports a libslic3r file ends with a
`PORT STATUS` trailer naming its source path, `confidence: high|medium|low`, its equality tier
and the oracle that proves it; that source path exists at the pin and matches the module's
manifest row; every `unsafe` block carries a `// SAFETY:` comment; and every port marker is one
of `// TODO(port):`, `// PERF(port):`, `// PORT NOTE:`, `// SAFETY:` or `// FIDELITY(port):`.
The command prints the count per marker kind.

### R15: Faithfulness is enforced and optimization is excluded

No requirement in this intent is a performance requirement, and no check in this repository gates
on throughput, instruction count or allocation. A knowingly slower translation is recorded as a
`// PERF(port):` marker and nothing else; `port/reports/perf-backlog.md`, generated from those
markers, is the handover to the following intent. The banned-substitution list rejects idiom
"improvements", including rounding the scaling conversions, substituting a standard hash map
where iteration order reaches output, and introducing a parallel reduction where the original's
order is load-bearing.

### R16: Scaffolding is counted down to zero before the end-to-end milestone is claimed

`just port-status` counts `todo!()`, `unimplemented!()` and modules gated out of the build. That
count is zero for every in-scope module before R21 is claimed. The same command fails on a
placeholder constant pattern: a numeric constant whose ported module's source line in the
vendored tree has a different value.

### R17: The vendored C and C++ libraries are called, not reimplemented

Clipper2 (which the vendored copy patches, so no published crate matches it), Boost.Polygon's
Voronoi builder, admesh, libnest2d, qhull and NLopt are bound through FFI against the vendored
sources, exactly as they are at the pin. A check fails if any crate manifest depends on a named
substitute for one of them. Replacing them with Rust implementations is out of scope for this
intent.

### R18: The order-dependence hazards are audited and the port's choices are recorded

Two committed audits, each regenerated by a command: every unordered container that is iterated
rather than only looked up, and every comparator that is not a total order. For each site the
audit records the port's choice and whether it diverges from the oracle. Each such site in the
port carries a `// FIDELITY(port):` marker. The port sums in a fixed order, uses total-order
comparators and uses insertion-ordered maps where iteration order reaches output, so it is
deterministic where the oracle is not; `port/reports/divergences.md` names every place that makes
the port differ from the oracle and the level it is checked at instead.

### R19: Every ported unit is proven equal against the real oracle, at its declared tier

A unit's test runs the vendored C++ — through FFI to the library built from the pin, or against
the committed stage dumps — and compares at the tier its manifest row declares: exact equality of
integer-coordinate output for fixed-point units, a declared tolerance and a declared comparison
function for float units. No test substitutes a stand-in for the code under test or for the
oracle. Fixed-point units that take polygons or points additionally have a differential fuzz
target against the C++ through FFI.

### R20: The benchy is compared stage by stage from the first ported unit

`just compare-stages` slices the benchy fixture with the port and compares, for every stage the
manifest marks as ported, the port's stage output against that stage's oracle dump at the stage's
declared tier, and reports the first stage that differs.

### R21: The benchy is sliced by the port and by the oracle, and the G-code is compared

`just compare-benchy` slices the committed benchy fixture with the port and with the pinned
oracle, from the same resolved config, and reports the level reached. The port reaches L1 on the
base configuration recorded in `port/reports/determinism.md`.

### R22: The port is usable to slice files for 3D printing on a Bambu printer

Both hold: `just compare-fixtures` reports L1 for the port against the oracle on each fixture in
the committed set, with the Bambu Lab X1 Carbon 0.4 nozzle machine, the `0.20mm Standard @BBL
X1C` process and the `Bambu PLA Basic @BBL X1C` filament; and a person prints the port's benchy
G-code on a Bambu X1 Carbon and the print completes. The second is the owner's acceptance, not a
correctness gate: where the first holds the port's G-code is identical to the oracle's, so the
print says the same about both.

### R23: The oracle checks run where the oracle can run, and never block document work

`.asdlc/checks` holds the document checks and the code checks that need neither the oracle binary
nor a built libslic3r. The checks that only read the vendored source — the source paths and
manifest rows in R14, the placeholder-constant check in R16 — are in that set, and the jobs that
run it initialise the submodule shallowly, since it is pinned and shallow. Every check that needs
the oracle binary, a local libslic3r build, or a comparison against either runs in a separate
macOS arm64 CI job. A task that touches no code still passes with the document checks alone.

### Two oracles, and which is which

The pinned v2.5.2 release binary is the cheap oracle: it slices headlessly with no GUI and no
display, in under a second for the benchy, and its presets must come from
`vendor/OrcaSlicer/resources/profiles/BBL/` because the app bundle's own presets are packed into
an opaque archive. It answers the end-to-end question the intent names, and nothing else — it
cannot say which stage first diverged.

The locally built `libslic3r` is the fine oracle. It is built with the GUI off and CAD on, the
one such combination upstream itself exercises, and with `-ffp-contract=off`, which is a build
flag and not a source change: on this architecture the compiler otherwise fuses multiply-add
expressions that Rust never fuses, including the two-dimensional cross product that decides
orientation branches at many call sites. Its stage dumps come from
`Print::set_slicing_pipeline_hook_fn`, which is public, pure C++, fires at the
`SlicingPipelineStepPlugin` seams listed in `vendor/OrcaSlicer/src/libslic3r/Print.hpp`, is armed
by a config option, and which upstream tests leaves the exported G-code byte-identical when the
hook does nothing. The debug macros are deliberately not used for this: defining them undefines
`NDEBUG` and `assert`, producing a different build from the oracle.

R6 measures whether the two agree instead of assuming it. The measured evidence is that a single
fused multiply-add never moved a nanometre-grid coordinate or a three-decimal G-code value in two
million trials, so they are expected to agree; if they do not, C2 owns the choice.

### What "the same output" rests on

Measured on the pinned release binary on this machine: across five runs of a cube, three of the
benchy and two of a third model, the only byte that ever changed in the G-code was the wall-clock
line, and the statistics and resolved-config JSON were byte-identical with no normalisation at
all. So the port needs no tolerance for nondeterminism on the base path, and L1 is the default
gate rather than an aspiration. The comparison order is: statistics JSON first, because it is
per-layer, per-feature and per-object numbers that diff cleanly; then the G-code, which the
`; FEATURE:`, `; Z_HEIGHT:` and per-object label comments localise to a layer, a feature and an
object; then raw bytes.

R3 extends that measurement to the configurations nobody has measured — tree support, the wipe
tower, multi-filament, fuzzy skin. The per-configuration gate table in `docs/ORACLE.md` is
produced from that report, not authored here: where the oracle is not reproducible against
itself, no amount of fidelity reaches L1 and the gate is L3 or L4. Three mechanisms are already
known to make that so: a float reduction over a concurrently filled vector feeding tree-support
node geometry, a float sum over hash iteration order in the wipe tower, and an entropy-seeded
thread-local generator in fuzzy skin.

Goldens are valid only for one platform: the mathematical library agrees bit for bit between Rust
and C++ here because both call the same system symbol, and the fused-multiply-add behaviour is
architecture-dependent. That is why R7 records the platform and R23 runs these checks on one.

### The fixtures

The benchy ships in the vendored tree as a Draco-compressed model. The fixture is produced once by
asking the pinned oracle to export it as STL, and the result is committed to `fixtures/` with its
basename frozen, because the model's basename is embedded in both the G-code and the statistics
JSON and a renamed copy produces a diff that has nothing to do with slicing. Both sides then read
the same committed file, and the port needs no Draco decoder. The model is public domain
(CC0 1.0), which the vendored tree does not record anywhere, so `vendor/README.md` records it.

### Scope, and why it is a manifest and not a list

Include analysis alone cannot scope this port in either direction. The headers the GUI names
reach only part of the library while leaving out mandatory slicing code; the model type drags in
SLA, texture-baking and project-format headers; and most of the library is reachable from the
shipped binary. So scope is computed by one script from the four entry points, with the
deductions named as reasons in rows, and the result is a file a command regenerates and CI
diffs. Everything downstream — plan steps, tasks, progress, the port's own checks — reads that
file. The same script carries a column for coverage-measured execution during a benchy slice,
populated when the local build exists; that turns the include-reachability number from an upper
bound into the measured subset, and it is not a precondition for anything.

Equality tiers are a manifest column because the criterion is not uniform. The fixed-point parts
of the library — the wall generator, most of the infill, the algorithm and execution helpers, and
the files with no floating-point involvement — are held to exact equality of integer-coordinate
output. The float parts are held to a declared tolerance with a declared comparison function.
The G-code itself is held to a level from R4.

### Order of work, and what the first comparison is

The intra-library include graph is acyclic, so crate boundaries follow its levels without
fighting cycles, and the pipeline drivers sit at the top of it. A strictly bottom-up port
therefore produces no complete G-code until nearly all of the library is ported, which is why
R20 exists: the first comparison against the vendored slicer is per-stage on the benchy, from the
first ported unit, and R21's end-to-end comparison is the acceptance gate rather than the first
output. C3 carries that reading back to the intent's author. No shim marshals the pipeline's
shared mutable object graph across a stage boundary in this intent: the boundary types are
object graphs, not values, and that cost is unmeasured.

### Faithful first, mechanically

Faithfulness is not a review sentiment here. It is: a contract written down before any unit is
ported (R12); a loop in which the implementer sees the original and the guide while two reviewers
see only the diff and are told to assume it is wrong (R13); a trailer and marker set a script
checks on every module (R14); a backlog that is the only place a deferred optimization may live
(R15); a burn-down of scaffolding to zero (R16); a ban on substituting Rust libraries for the
vendored ones (R17); and a differential test against the real C++ for every unit (R19). The
reference implementation is permanently available at a fixed path in the submodule, so every
review step can read the exact source file its module came from — which is the one mechanism in
the Bun port that caught semantic divergence before merge.

## How each constraint in the intent is met

| Constraint | Met by |
|---|---|
| The pin of the vendored slicer remains as it is. | Nothing in this spec edits the vendored tree or moves the submodule pointer. The only changes to how the reference behaves are build flags and FFI against its own sources (R6, R17), and every oracle output records the pinned commit (R7). The cost of that choice — that a few subsystems can then never be byte-matched — is C1. |

## Open questions from intent

### Q1: What is the exact workflow for porting, as per how the Bun Rust port worked?
- answer: answered

Answered from the Bun port's primary sources (its own account of the rewrite, and the public
commit carrying `docs/PORTING.md` and the batch driver), checked against what this codebase
allows. The workflow is written into `docs/WORKFLOW.md` and `docs/PORTING.md` by R13 and R12:
one source file to one Rust module; a Phase A draft that need not compile, which is what makes
wide parallelism possible; Phase B compiling bottom-up with compiler errors as the work queue;
one implementer, two adversarial reviewers in separate contexts seeing only the diff, one fixer;
the markers and the `PORT STATUS` trailer; a banned-substitution list the review stage rejects
on; the conflict discipline for agents sharing a worktree; and a three-unit trial before fan-out.

Four parts of that port do not transfer and are deliberately absent: its language-independent
test suite, which is why R3 to R6 build an oracle instead; its restructuring of its own source
tree, which the pin forbids and R8's manifest replaces; its single binary hosting both
implementations, for which no seam exists here; and its performance gates, which R15 excludes.
Its ownership-classification pass does not transfer either, because C++ states ownership in its
types; the equivalent pass here is the hand-designed template-heavy and header-only files named
in R13.

### Q2: What counts as "the same output" as the vendored slicer, and how is it compared?
- answer: answered

Answered by measurement on the pinned oracle and from upstream's own code. The levels, the
normalisation and the artifacts to compare are R4; the normalisation is exactly the four line
kinds upstream strips in `vendor/OrcaSlicer/tests/fff_print/test_slicing_pipeline_hook.cpp`;
the statistics and resolved-config JSON are compared with no normalisation at all. L1 — identical
bytes after that normalisation — is the gate for the base FFF path, which is measured to be
run-to-run byte-identical. The gate for every other configuration is produced by R3's report,
because where the oracle cannot reproduce itself no port can match it; the subsystems known to
be in that position, and the port's deliberate divergences, are recorded by R18 and carried as
C1.

### Q3: What does OrcaSlicer currently call in the library?
- answer: answered

Answered from the vendored code. Both drivers — the application's headless path and the GUI's
background slicing process — call the same four entry points: `Model::read_from_file`,
`Print::apply`, `Print::process` and `Print::export_gcode`. Scope is the include closure over
those, with named deductions, computed and kept current by R8's manifest; SLA is excluded by file
rather than by directory (R9). Three consequences are design decisions rather than open
questions: command-line option parsing belongs to the library and not to application code, so it
is in scope; the plate layer that supplies bed shape and wipe-tower placement lives in the GUI
library, so it is out of scope and the port takes resolved configuration instead (R10, R11); and
the Bambu-printer flag is set explicitly by the caller because validation depends on it.

## Areas of concern

### C1: Byte parity for some subsystems requires changing the oracle, which the pin forbids
- owner: Bruk Habtu

The intent asks for the same output as the vendored slicer, and for the pin to remain as it is,
with the old library as the oracle. For tree support, the wipe tower and fuzzy skin these cannot
both hold: the vendored slicer is not reproducible against itself there — a float reduction over
a concurrently filled vector feeds tree-support geometry, a float sum runs over hash iteration
order in the wipe tower, and fuzzy skin is seeded from entropy per thread — so no Rust port can
reach L1 against it, and reaching byte parity would mean patching the reference to be
deterministic, at which point the baseline stops being the old library.

This spec takes the side of the pin: build flags and FFI only, the Rust port made deterministic,
and the divergence named and checked at a looser level (R18, and the gate table from R3). The
proposal to the owner is to accept that, with the alternative being an explicitly reviewed
determinism overlay on the oracle for those subsystems, recorded in `vendor/README.md` and
treated like a pin move. R3 tells us how much is actually at stake before anyone decides.

### C2: The two oracles may disagree, and then one of them is not "the old library"
- owner: Bruk Habtu

The released binary is built as shipped; the local build adds `-ffp-contract=off` so the
reference matches Rust's arithmetic semantics and stops being architecture-dependent. Both are
built from the pinned commit, and the measured evidence says the difference should not reach a
printed coordinate, but it is unmeasured for this library. R6 measures it. If the two disagree
materially, the owner decides which is normative — the binary a user would actually run, or the
build the port can match — and whether goldens are then per-oracle. The same choice fixes the
platform: these goldens are valid for one operating system and architecture only.

### C3: "A benchy as a first output" and a bottom-up port pull against each other
- owner: Bruk Habtu

The intent names slicing a benchy and comparing the results as the first output. The library's
pipeline drivers sit at the top of its dependency graph, so an end-to-end G-code comparison
through the port is only possible once nearly all of the library is ported. This spec reads "first
output" as the first comparison and makes it per-stage on the benchy from the first ported unit
(R20), with the end-to-end comparison as the acceptance gate (R21). The alternative is a
throwaway bridge that serves unported stages from the vendored C++, which would make a mixed
end-to-end slice possible much earlier; its cost is unmeasured, and the boundary marshals a shared
mutable object graph rather than values. The owner decides whether the per-stage reading is the
one they meant.

### C4: At the end of this intent the port still links C++
- owner: Bruk Habtu

R17 binds the vendored Clipper2 — which the vendored copy patches in two behaviour-changing ways
that no published crate carries — along with Boost.Polygon's Voronoi builder, admesh, libnest2d,
qhull and NLopt. That is the only way to be exact by construction, and it keeps those diffs out of
the way while the library itself is validated. It also means "the slicer lib is ported to Rust" is
true of libslic3r and not of everything it links. The proposal is to accept it for this intent and
let a later intent replace each one, validated against the FFI build.

### C5: Equality of G-code is necessary and not sufficient
- owner: Bruk Habtu

A faithful translation of C++ pointer discipline reaches for `unsafe`, and the compiler is
entitled to assume away what the original did by convention. In the Bun port, undefined behaviour
reachable from ordinary safe code was found by an outsider hours after a fully green suite of over
a million assertions merged. This spec requires a `// SAFETY:` comment on every `unsafe` block
(R14) and nothing more; sanitizers, Miri and fuzzing beyond R19's differential targets are not
requirements here. The owner decides whether that belongs in this intent or the next.

### C6: 3MF project files are out of scope, and that is how Bambu users work
- owner: Bruk Habtu

R11 takes resolved configuration as the port's input and defers the project-format and preset
layers, which is what keeps a benchy difference attributable to slicing. The consequence is that
at the end of this intent the port slices a mesh plus a resolved config, not a 3MF project from
the slicer's own workflow, and the preset and project-format readers are by far the largest files
in that layer. Whether "usable to slice files for 3D printing" (R22) is met without them is the
owner's call.

### C7: The fine oracle depends on a build nobody has exercised on this platform
- owner: Bruk Habtu

Building the library with the GUI off is supported by the upstream CMake logic and used by one
upstream script, but only inside Linux, only for one test target, and never on macOS; the vendored
documentation itself calls it untested. The dependency superbuild also still requires most of the
heavy libraries with the GUI off, and no part of it is prebuilt here. If that build cannot be made
to work, R5, R6, R19 and R20 lose their per-stage oracle and the only comparison left is
end-to-end, which cannot localise a divergence to a stage. The proposal is to attempt it early, as
its own piece of work, and to report back rather than work around it.

### C8: The size of this intent is not a schedule, and nothing here makes it smaller
- owner: Bruk Habtu

Scope is around 245,000 lines across roughly 420 files, before any deduction a coverage run might
justify. The Bun port spent about $165,000 of model time on a larger but far easier language pair,
over eleven days to merge and three and a half months to a stable release, with nineteen
regressions and a dedicated divergence audit that still found high-risk divergences after a fully
green suite. This spec is written so the work can proceed and be checked piece by piece, and so
that no single piece has to be finished for the rest to be verifiable; it does not shorten the
work. The owner should know that before the plan is cut.
