# Spec: Port libslic3r to Rust with 1:1 functionality

libslic3r at the pin is 607 source files and about 340,000 lines. This spec does not shrink that.
It fixes the things every later piece of work needs to agree on — the oracle, what "the same
output" means, what is in scope, how one ported unit is proven equal, and how "faithful first"
is enforced — and pushes all per-file detail into generated artifacts that a task commits and a
script re-checks. Where this spec states a count or a measurement, it either names the committed
command that reproduces it (R3, R8) or names the source it came from.

## Requirements

### R1: One command produces the pinned oracle binary, and refuses any other version

`just oracle-fetch` downloads the OrcaSlicer v2.5.2 release asset
`OrcaSlicer_Mac_universal_V2.5.2.dmg` into its own directory outside `/Applications`, verifies
its sha256 against the value `vendor/README.md` records, verifies the binary reports `2.5.2`,
and exits non-zero otherwise. The recorded value is
`6ea1afcdffb7e9ab011e2d6f6db665cb18463d1c4774591cd5db7ee0225479d9`, measured on a download of
that asset during this intent's research and committed to `vendor/README.md` before the first
fetch, so the check is not circular; a mismatch fails the command rather than rewriting the
value. The installed `/Applications/OrcaSlicer.app` (2.4.2) and `BambuStudio.app` are never read
by any command in this repository.

### R2: One command runs the oracle on a named configuration, and fails rather than producing nothing

`just oracle-slice <fixture> <configuration>` runs the pinned oracle from a scratch working
directory and exits non-zero unless a non-empty `plate_1.gcode` was written. `<configuration>`
names a row in `docs/ORACLE.md`, and that row holds the machine, process and filament preset
paths under `vendor/OrcaSlicer/resources/profiles/BBL/` plus the explicit setting overrides that
switch the configuration's feature on. The command always passes `--outputdir`, an explicit
`--load-filaments`, and `--arrange 0` (R24). It maps the oracle's negative exit codes (received
by the shell modulo 256) to named failures.

### R3: A committed report records the oracle's run-to-run reproducibility per configuration

`port/reports/determinism.md` has one row per comparison configuration named in `docs/ORACLE.md`
— base FFF; tree support; wipe tower and multi-filament; fuzzy skin; and any other the port needs
— and one sub-row per compared artifact: the G-code, the `--export-settings` JSON and the
`--export-statistics` JSON. Each sub-row names the normalisation R4 declares for that artifact,
and records whether at least five runs of that configuration were byte-identical with no
normalisation, with that normalisation, or not at all. Five runs per configuration is the
minimum. The sub-row's gate is the strongest R4 level all five runs reach against each other, and
`none` where they reach no level; `docs/ORACLE.md`'s gate table carries the same artifact
breakdown. The base FFF row carries the
measurement this spec's design rests on; it is produced by the committed command and not quoted
from anywhere. The report is regenerated by a committed command.

### R4: A committed comparator reports which level of sameness two outputs reach

One comparator takes two G-code files and evaluates each level below independently, reporting
every level that passes, the strongest of them, and the first failing location at the next
stronger level. When no level passes it reports `none` and the first differing byte. The levels
are ordered strongest to weakest and are not assumed to be nested, which is why the comparator
evaluates each one rather than stopping at the first pass:

- **L0** identical bytes.
- **L1** identical bytes after the declared normalisation.
- **L2** identical token stream (command plus axis words, comments dropped).
- **L3** identical move count and order, numbers within the declared per-axis tolerance,
  reporting max and RMS deviation per axis.
- **L4** per-layer and per-role aggregates (move count, extruded length, E delta, bounding box,
  travel distance, layer count) within the declared aggregate tolerance.

The declared normalisation is exactly the four line kinds upstream itself strips in
`vendor/OrcaSlicer/tests/fff_print/test_slicing_pipeline_hook.cpp`: `; generated by `,
`; model label id: `, lines containing `printing object, unique label id: `, and lines
containing `slicing_pipeline_plugin`. Nothing else is normalised in the G-code.

Every tolerance in this repository defaults to exact: zero per-axis deviation and zero aggregate
deviation. A looser tolerance exists only as a `tolerance` and `comparison function` value on a
manifest row (R8) or a `docs/ORACLE.md` configuration row, and only with a reason in that row.
No requirement, test or report uses an undeclared tolerance.

The oracle's `--export-settings` JSON is compared byte for byte with no normalisation; the
normative run for it is the one with the pipeline hook unarmed, and where the compared pair
includes an armed run (R5) the `slicing_pipeline_plugin` key is allowed to differ, because
arming the hook requires that key to be non-empty (`src/libslic3r/Print.cpp:3308`). The
`--export-statistics` JSON is compared with one field normalised, `generator`, which the oracle
writes as the static string `SLIC3R_APP_NAME + " " + SoftFever_VERSION`
(`src/libslic3r/GCode/GCodeStatistics.cpp:177`) and which the port therefore cannot reproduce
without claiming to be OrcaSlicer.

### R5: A per-stage oracle dumps the pipeline's intermediate state without changing its output

A committed C++ dumper links the vendored `libslic3r` built from the pin and registers a hook
with `Print::set_slicing_pipeline_hook_fn` (`vendor/OrcaSlicer/src/libslic3r/Print.hpp:1064`).
The hook's signature is `void(Print&, const PrintObject*, SlicingPipelineStepPlugin)`
(`Print.hpp:1061`): it carries no layer, so it fires once per step, and the dumper walks the
object's layers itself at each seam. It is armed only when the `slicing_pipeline_plugin` config option is non-empty
(`Print.cpp:3308`), which is why that line is in R4's normalisation.

The dumper writes one dump per seam that fires. The seams are exactly these, and no later
document restates them:

- Nine per-object seams that fire for a sliced object: `posSlice`, `posPerimeters`,
  `posPrepareInfill`, `posInfill`, `posIroning`, `posContouring`, `posSupportMaterial`,
  `posDetectOverhangsForLift`, `posSimplifyPath`.
- Two print-wide seams, which pass a null object: `psWipeTower`, `psSkirtBrim`.
- `posEstimateCurledExtrusions` has a fire site (`Print.cpp:3506`) that cannot fire for a sliced
  object, because its `hook_after` requires `is_step_done(posEstimateCurledExtrusions)` and
  `PrintObject.cpp:1054` has that `set_done` commented out; the only live `set_done` is
  `Print.cpp:3510`, in the branch for objects that are not sliced, where no hook runs. The
  dumper does not rely on it.
- `psGCodePostProcess` is excluded: the enum's own comment says it fires from the GUI G-code
  post-process seam and not from `Print::process()`, it is dispatched only from
  `src/slic3r/plugin/`, which R10 puts out of scope, and it fires after the file is written.
- `psGCodeExport`, `psConflictCheck`, `posSimplifySupportPath`, `posSimplifyWall` and
  `posSimplifyInfill` are real pipeline steps with no value in `SlicingPipelineStepPlugin` and
  therefore no seam at all. G-code emission and conflict check are compared end to end only
  (R20). C11 carries that gap.

Dumps serialise integer `coord_t` coordinates and never round-trip through float. A check proves
the dumping build's exported G-code is identical at L1 to the same build with the hook
unregistered — at L1 and not byte for byte, because arming the hook adds a
`slicing_pipeline_plugin` line to the exported config block, which is the fourth line kind R4
normalises and the same comparison upstream makes.

### R6: A committed report records whether the two oracles agree

`port/reports/oracle-parity.md` records, for the fixture set (R25), whether the locally built
`libslic3r` and the pinned release binary reach L1 against each other, and lists every
difference found. It names the built oracle's exact CMake flags, including `-ffp-contract=off`.

### R7: Every oracle output records what produced it

Each golden file, dump and report carries a header recording: the pinned commit
`f92a7c065c5718b8ef1baac1cd704df2911238f4`; which oracle produced it and its build flags; OS;
architecture; compiler version; the value of `SCALING_FACTOR`; the full preset set and
configuration overrides; the fixture's basename; and the fixture's resolved instance transform
(R24).

### R8: A committed, regenerated manifest is the authority on scope and progress

`port/manifest.tsv` has one row per libslic3r source file at the pin, with columns: path,
subsystem, lines, file-level include-DAG level, crate-level level, in scope or out with a reason,
target crate and module, pipeline stage or `none`, equality tier, tolerance, comparison function,
proof path (R19), and status. A committed script regenerates it; re-running the script leaves the
file unchanged.

**The file set.** One row per `.h`, `.hpp`, `.cpp` or `.mm` file under
`vendor/OrcaSlicer/src/libslic3r` at the pin. That set is 607 files and 340,112 lines counted as
`cat | wc -l`; it includes `MacUtils.mm` and `Format/ModelIO.mm`, which
`src/libslic3r/CMakeLists.txt:604-610` appends under `if (APPLE)` and which are therefore part of
the library on the macOS arm64 platform R7 and R23 pin. It excludes the generated
`libslic3r_version.h`, which exists in the tree only as `libslic3r_version.h.in`. The script
asserts the row count against that set rather than against a number written here.

**The scope algorithm.** Include closure alone provably cannot reach several core slicing files,
because they have no header: `LayerRegion.cpp` (1,129 lines, defining
`LayerRegion::make_perimeters` and `LayerRegion::prepare_fill_surfaces`, declared in
`Layer.hpp`), `ContourZ.cpp` and `BeltPurge.cpp` have no `.hpp` sibling and no `#include` in the
tree reaches them. So scope is computed in four passes:

1. The include closure over the four entry points `Model::read_from_file`, `Print::apply`,
   `Print::process` and `Print::export_gcode`.
2. The same-stem `.cpp` sibling of every header in the closure.
3. An orphan pass: every `.cpp` that defines methods of a class declared in an in-closure header.
4. The named deductions below.

The script asserts that `LayerRegion.cpp`, `ContourZ.cpp` and `BeltPurge.cpp` are present in the
result, since passes 1 and 2 alone cannot produce them.

**The deductions**, each with its reason in the row:

| Group | Reason |
|---|---|
| GUI-only mesh, measure and gizmo helpers | No caller in the four entry points' closure. |
| Parametric CAD | No caller in the four entry points' closure. |
| SLA, by file | R9. |
| Arrange and orient | R24 fixes placement in the fixture and R2 passes `--arrange 0`, so no arranger runs in any comparison; the CLI reaches `ModelArrange::arrange_objects` only from `--copy` (`src/OrcaSlicer.cpp:5026-5040`), which no configuration uses, and its default path (`:5637`) is driven by `Slic3r::GUI::PartPlate`, which R10 puts out of scope. C14 carries the deduction, because the application does call this code. |
| Texture baking | No caller in the four entry points' closure. |
| Project-format readers under `Format/` other than `STL` | R11 and C6. `Model::read_from_file` dispatches `.drc`, `.amf` and `.3mf` into these loaders (`Model.cpp:462-470`), including `Format/bbs_3mf.cpp` at 10,211 lines; the port's input is a committed STL plus a resolved config, so `Format/STL.{cpp,hpp}` stays in scope and the rest is out. |
| The preset layer (`Preset.cpp` 5,266 lines, `PresetBundle.cpp` 9,351 lines, `PresetCacheFormat.cpp` 666 lines) | R11 and C6. The port's configuration input is the oracle's resolved config, not preset JSON. |
| Files no caller in the vendored tree reaches | Dead at the pin. |

`GCode/GCodeStatistics.{cpp,hpp}` is **in** scope. The application calls it
(`src/OrcaSlicer.cpp:7231`), so the intent's scope rule puts it in, and the port emits
`plate_N.statistics.json`; R4 says how it is compared.

**Crate levels.** The intra-library include graph is acyclic at file granularity, verified by
running Tarjan over the library's C and C++ sources and finding no non-trivial strongly connected
component, but at module granularity it is one large cycle: 5 components for 43 modules, one of
which holds 39 modules and 321,722 of 337,335 lines. Crate
boundaries are drawn over modules, so the script computes and commits a named feedback-arc cut —
each cut edge as a file and the header it includes — and derives the crate-level level from the
cut graph, so re-running is deterministic. The mutual clusters the cut cannot break cheaply,
`GCode.cpp` with `GCode/*` and `Model` with `Format`, are single crates. C10 owns the cut,
because it is a choice and not a derivation.

No later document restates the file list, the seam list or the cut; each reads the artifact.

### R9: SLA is excluded by file, not by directory

The manifest marks each `SLA/` file in or out individually with its reason. `SLA/IndexedMesh` is
in scope because Z-contouring calls it (`ContourZ.cpp`, `AABBMesh.cpp`, `PrintObject.cpp`,
`Layer.hpp`); the SLA fields carried on the model type are ported as data only; the hollowing,
pad and concave-hull implementations are out. C9 carries the tension with the intent's "SLA is
not ported".

### R10: The port's slicing surface is the GUI-free sequence, and the plate layer is out of scope

The port exposes the sequence `vendor/OrcaSlicer/tests/fff_print/test_helpers.hpp` uses — build a
model, apply a config, validate, process, export G-code — and nothing from
`src/slic3r/GUI/PartPlate`. The port runs no arranger: `init_print`'s own `arrange` parameter
(`test_helpers.hpp:88`, default `true`) is not part of the surface, because R24 fixes placement
in the fixture instead. Bed shape, exclusion areas, wipe-tower placement and filament maps reach
the port as resolved configuration values (R11). The Bambu-printer flag the oracle derives from
the printer model is set explicitly by the caller, because validation and G-code depend on it.

### R11: The port's configuration input is the oracle's resolved config, not preset JSON

The port consumes the resolved configuration the oracle writes with `--export-settings` on an
unarmed run, which is byte-stable across runs. Preset files, the `inherits` chain and
preset-bundle resolution are out of scope for this intent, so a benchy difference cannot be
caused by preset resolution. Emission is not resolution and is in scope: the port writes the
G-code `HEADER_BLOCK` and `CONFIG_BLOCK` from that resolved input, selecting and formatting the
same keys the oracle writes (`src/libslic3r/GCode.cpp:4255-4335`), and the print-time estimator
whose line the header carries (`src/libslic3r/GCode/GCodeProcessor.cpp:1310`) is in scope, since
L1 compares both. The two keys that exist only in the G-code config block,
`first_layer_temperature` and `first_layer_bed_temperature`, are derived by the port at emission
time. Resolved configs are generated with a throwaway data directory so no print-host credential
field is ever committed.

### R12: `docs/PORTING.md` states the per-file translation contract

It is committed before any unit is ported and contains: the crate map, which agents may not
invent; a type map; an idiom map; a don't-translate list; a banned-substitution list; and these
rules, each of which this codebase makes load-bearing:

- The five scaling entry points do not behave alike, so the rule is stated per API. For integral
  output, `scaled<coord_t>()` and the Eigen overload (`Point.hpp:674-677`, `:681-690`) are
  truncating division by the `SCALING_FACTOR` global; port them as truncating division, and
  adding rounding is banned (the `std::round` on `Point.hpp:676` is commented out in the
  original). The `scale_()` macro (`libslic3r.h:106`) is a plain `double` division that truncates
  nothing, and the floating-output `scaled<Tout>()` overload (`Point.hpp:663-666`) does not
  truncate either; where the original converts their result to an integer type, the port
  reproduces that truncation at the call site, not inside the API. `unscale_()`
  (`libslic3r.h:107`), `unscale<T>()` (`libslic3r.h:138`) and `unscaled<T>()`
  (`Point.hpp:697-699`) are multiplications by the global and never truncate. In every case the
  port divides by the global and never multiplies by its reciprocal.
- Mirror `f32` and `f64` exactly where the original uses `float` and `double`. Widening a
  `float` field changes every emitted E value.
- Two rounding modes coexist: ties-away in the G-code formatter and in Clipper2 point
  construction, ties-to-even in Clipper2 intersections. Each site is ported individually.
- Never widen or narrow an error set. A function that cannot fail does not return `Result`; an
  assertion compiled out in the oracle's release build does not become a live panic.
- Format numbers locale-independently; transcribe the G-code formatter's digit counts,
  zero-padding, decimal insertion and trailing-zero stripping verbatim.
- Never reimplement a linked C or C++ library in Rust in this intent (R17).

### R13: `docs/WORKFLOW.md` states the porting workflow

It is committed before any unit is ported and states: the unit of work (one libslic3r source file
plus its header to one Rust module, except the template-heavy and header-only files, which are
hand-designed once, before fan-out); the two phases, where a Phase A draft is not required to
compile and Phase B compiles bottom-up by the crate-level level R8's cut defines, with compiler
errors as the work queue; the loop of one implementer, then two adversarial reviewers in separate
contexts who each read the diff **and** the vendored source file the module came from, are told
to assume the module is wrong, cite every divergence as `source:line` against `module:line`, and
may not implement, then one fixer; the rejection rule that a workaround needing a paragraph of
justification is wrong code; the conflict discipline for agents sharing a worktree (commit named
files only, no `git stash` or `git reset`, no build commands, no slow commands); and a three-unit
trial run, covering one unit of each equality tier, whose output corrects `docs/PORTING.md`
before fan-out.

### R14: Every ported module is greppable, and a script checks it

`just port-status` fails unless: every Rust module that ports a libslic3r file ends with a
`PORT STATUS` trailer naming its source path, `confidence: high|medium|low`, its equality tier
and the oracle that proves it; that source path exists at the pin and matches the module's
manifest row; every `unsafe` block carries a `// SAFETY:` comment; every ported numeric constant
carries a `// PORT SRC: <vendored path>:<line>` marker beside it; and every port marker is one of
`// TODO(port):`, `// PERF(port):`, `// PORT NOTE:`, `// SAFETY:`, `// PORT SRC:` or
`// FIDELITY(port):`. The command prints the count per marker kind.

### R15: Faithfulness is enforced and optimization is excluded

No requirement in this intent is a performance requirement, and no check in this repository gates
on throughput, instruction count or allocation. A knowingly slower translation is recorded as a
`// PERF(port):` marker and nothing else; `port/reports/perf-backlog.md`, generated from those
markers, is the handover to the following intent. The banned-substitution list rejects idiom
"improvements", including rounding the scaling conversions, substituting a standard hash map
where iteration order reaches output, and introducing a parallel reduction where the original's
order is load-bearing.

### R16: Scaffolding is counted down to zero before the end-to-end milestone is claimed

`just port-status` counts `todo!()`, `unimplemented!()` and modules gated out of the build. That
count is zero for every in-scope module before R21 is claimed. The same command fails on a
placeholder constant: a numeric constant whose `// PORT SRC:` marker (R14) names a vendored line
that does not contain that literal.

### R17: The vendored and superbuild C and C++ libraries are called, not reimplemented

Clipper2 (which the vendored copy patches, so no published crate matches it), admesh, libnest2d
and qhull are bound through FFI against the vendored sources in `vendor/OrcaSlicer/deps_src/`,
exactly as they are at the pin. Boost.Polygon's Voronoi builder — used at
`src/libslic3r/Geometry/Voronoi.hpp` and `Arachne/SkeletalTrapezoidation.hpp` — has no vendored
source: Boost is a superbuild project under `vendor/OrcaSlicer/deps/Boost/`, so it is bound
against the version that recipe pins. NLopt is likewise a superbuild project
(`deps/NLopt/NLopt.cmake` fetches v2.5.0 by URL with a sha256) and is bound only if the manifest
marks an in-scope caller; at the pin it is absent from `src/libslic3r/CMakeLists.txt`'s
`target_link_libraries`, reaches libslic3r only transitively through libnest2d, and its only
libslic3r includer is `SLA/SupportTreeBuildsteps.cpp`, which R9 puts out of scope. A check fails
if any crate manifest depends on a named substitute for one of them. Replacing them with Rust
implementations is out of scope for this intent.

### R18: The order-dependence hazards are audited and the port's choices are recorded

Two committed audits, each regenerated by a command: every unordered container that is iterated
rather than only looked up, and every comparator that is not a total order. For each site the
audit records the port's choice and whether it diverges from the oracle. Each such site in the
port carries a `// FIDELITY(port):` marker. The port sums in a fixed order, uses total-order
comparators and uses insertion-ordered maps where iteration order reaches output, so it is
deterministic where the oracle is not; `port/reports/divergences.md` names every place that makes
the port differ from the oracle and the level it is checked at instead.

### R19: Every ported unit is proven equal against the real oracle, at its declared tier

A unit's test runs the vendored C++ and compares at the tier its manifest row declares: exact
equality of integer-coordinate output for fixed-point units, the row's declared tolerance and
comparison function for float units (R4). The row's `proof path` column names which of three
mechanisms the unit uses, so a task for any file says which one applies:

1. FFI to the library built from the pin, for externally linked symbols.
2. The committed stage dumps (R5), for whole pipeline steps.
3. A test translation unit inside the FFI crate that `#include`s the vendored `.cpp`, for
   internal-linkage code — 49 of 268 `.cpp` files declare an anonymous namespace and 112 declare
   static free functions, none of which has external linkage, and the pin forbids adding an
   export. Including the vendored file does not modify it, so the pin holds. Where even that is
   not possible the row says so and the helper is proven through its enclosing file's exported
   surface.

No test substitutes a stand-in for the code under test or for the oracle. Fixed-point units that
take polygons or points additionally have a differential fuzz target against the C++ through FFI.

### R20: The benchy is compared stage by stage from the first completed pipeline step

`just compare-stages` slices the benchy fixture with the port and compares, for every stage the
manifest's `pipeline stage` column marks as fully ported, the port's stage output against that
stage's oracle dump at the stage's declared tier, and reports the first stage that differs. The
gate applies from the first completed pipeline step, not the first ported unit: no stage output
exists until every file that stage reaches is ported. For the stages with no seam (R5) — G-code
emission and conflict check — the command falls back to R4's levels on the exported G-code,
localised by the `; FEATURE:`, `; Z_HEIGHT:` and per-object label comments, and says so in its
output rather than reporting the last seam as the first difference.

### R21: The benchy is sliced by the port and by the oracle, and the G-code is compared

`just compare-benchy` slices the committed benchy fixture with the port and with the pinned
oracle, from the same resolved config and the same instance transform (R24), and reports the
level reached. The port reaches the level `port/reports/determinism.md` records as the base FFF
configuration's G-code gate, and matches that configuration's statistics-JSON gate as well.

### R22: The port and the oracle produce the same G-code on every committed fixture

`just compare-fixtures` reports, for the port against the oracle on each fixture in the committed
set (R25) with the Bambu Lab X1 Carbon 0.4 nozzle machine, the `0.20mm Standard @BBL X1C` process
and the `Bambu PLA Basic @BBL X1C` filament, the level `port/reports/determinism.md` records as
that configuration's G-code gate. Whether that makes the port "usable to slice files for 3D printing",
and the owner's own print on an X1 Carbon, are C6.

### R23: The oracle checks run where the oracle can run, and never block document work

`.asdlc/checks` holds the document checks and the code checks that need neither the oracle binary
nor a built libslic3r. The checks that only read the vendored source — the source paths and
manifest rows in R14, the placeholder-constant check in R16, the document-section checks in R29 —
are in that set, and the jobs that run it initialise the submodule shallowly, since it is pinned
and shallow. Every check that needs the oracle binary, a local libslic3r build, or a comparison
against either runs in a separate macOS arm64 CI job. A task that touches no code still passes
with the document checks alone.

### R24: Object placement is fixed by the fixture, and no arranger runs in a comparison

Every comparison slices its objects at known transforms, and every fixture in R25's set holds one
object, so its record names one transform; the multi-filament configuration assigns more than one
filament to that single object rather than adding a second one. `just oracle-slice` always passes
`--arrange 0`, which sets the CLI's `need_arrange` to false (`src/OrcaSlicer.cpp:5072-5078`) —
necessary because `need_arrange` starts true (`:1576`) and is set true again for every mesh input
(`:1951`), and because the CLI's default arrange path (`:5637`) runs through
`Slic3r::GUI::PartPlate`, which R10 puts out of scope. Each committed fixture's mesh is already
positioned on the target plate, so the oracle's only remaining placement step is the Z-only
`ModelObject::ensure_on_bed` it applies to every mesh input (`:2003`, `Model.cpp:1896-1921`). The
fixture record (R25) names the single resolved instance transform, R7 records it, and the port
slices that transform. `just compare-benchy` and `just compare-fixtures` fail if the oracle's run
reports an object bounding box the fixture record does not name.

### R25: The committed fixture set is enumerated, and adding one is a recorded act

`fixtures/` holds exactly these, basenames frozen because the model's basename is embedded in
both the G-code and the statistics JSON:

| Frozen basename | Produced from | Used by |
|---|---|---|
| `3DBenchy.stl` | `vendor/OrcaSlicer/resources/handy_models/3DBenchy.drc` | R20, R21, R22 |
| `20mm_cube.stl` | `vendor/OrcaSlicer/tests/data/20mm_cube.obj` | R3, R22 |
| `frog_legs.stl` | `vendor/OrcaSlicer/tests/data/frog_legs.obj` | R3, R22 |

Each is produced once by asking the pinned oracle to export the vendored model as STL, already
positioned on the plate (R24), so both sides read the same committed file and the port needs no
Draco decoder. A fixture is added only by committing a row in `vendor/README.md` naming its
frozen basename, the vendored path it came from, the resolved instance transform, and the license
the model's publisher states — and saying so explicitly where upstream records none, which is the
case for `resources/handy_models/`, a directory with no license file. Every `docs/ORACLE.md`
configuration row names the fixtures it uses.

### R26: Every in-scope manifest row has a ported module before the end-to-end gates are claimed

`just port-status` fails while any manifest row marked in scope has a status other than ported,
and prints how many rows remain. R21 and R22 are not claimed until it passes. R14 checks the
module-to-manifest direction; this is the manifest-to-module direction, so an in-scope file that
was never ported cannot pass silently.

### R27: The port meets the gate every configuration's row declares

`just compare-configurations` runs the port against the oracle for each configuration named in
`docs/ORACLE.md` — base FFF, tree support, wipe tower and multi-filament, fuzzy skin — and fails
unless each reaches, for each compared artifact, the level `port/reports/determinism.md` records
as that configuration's gate for it. Where a gate is `none`, the command reports the divergence against R18's
`port/reports/divergences.md` and does not fail. C12 carries the risk that a configuration cannot
be constructed through the pinned CLI at all.

### R28: Each port unit's pull request shows the workflow was followed

A port unit's pull request body records both review verdicts from R13's loop, each citing
`source:line` against `module:line`, and names the module's manifest row. A check fails the pull
request otherwise. The three-unit trial run is recorded the same way, in `docs/WORKFLOW.md`,
before any fan-out pull request is opened.

### R29: A command checks that the two contract documents say what they must

`just port-status` fails unless `docs/PORTING.md` contains the sections R12 names — crate map,
type map, idiom map, don't-translate list, banned-substitution list, and the six rules — and
`docs/WORKFLOW.md` contains the sections R13 names — unit of work, the two phases, the loop, the
rejection rule, the conflict discipline, and the trial-run record. The check reads headings, not
prose quality.

### R30: A committed ownership manifest classifies every raw pointer before fan-out

`port/ownership.tsv` has one row per raw-pointer field, and per field that is a container of raw
pointers, declared in a header the manifest (R8) marks in scope, with columns: header path, line,
declaring type, field, C++ type, class (`owned`, `shared`, `borrowed`, `back-reference`, `ffi` or
`unknown`), the `path:line` of the evidence for that class, and the Rust type porters use. A
committed script lists the fields from the vendored headers and fails if a field has no row, a row
names a field that does not exist at the pin, or a row other than `unknown` has no evidence. The
file is committed before the first fan-out port unit's pull request is opened, and
`docs/PORTING.md` tells porters to take the Rust type from it verbatim. `just port-status` prints
the count of `unknown` rows.

### Two oracles, and which is which

The pinned v2.5.2 release binary is the cheap oracle: it slices headlessly with no GUI and no
display, in under a second for the benchy, and its presets must come from
`vendor/OrcaSlicer/resources/profiles/BBL/` because the app bundle's own presets are packed into
an opaque archive. It answers the end-to-end question the intent names, and nothing else — it
cannot say which stage first diverged.

The locally built `libslic3r` is the fine oracle. It is built with the GUI off and CAD on, the
one such combination upstream itself exercises, and with `-ffp-contract=off`, which is a build
flag and not a source change: on this architecture the compiler otherwise fuses multiply-add
expressions that Rust never fuses, including the two-dimensional cross product that decides
orientation branches at many call sites. Its stage dumps come from
`Print::set_slicing_pipeline_hook_fn`, which is public, pure C++, armed by a config option, and
which upstream's own test leaves the exported G-code identical to an unhooked run after exactly
the four-line normalisation R4 declares — not byte for byte, because arming the hook writes its
own `slicing_pipeline_plugin` key into the G-code's config block. The seams it fires at are
enumerated once, in R5, and they do not cover the pipeline: there is no seam at G-code export,
which is the largest in-scope subsystem and the one that produces the artifact R21 and R22
compare. C11 owns that. The debug macros are deliberately not used for this: defining them
undefines `NDEBUG` and `assert`, producing a different build from the oracle.

R6 measures whether the two agree instead of assuming it. They are expected to agree, because a
single fused multiply-add is very unlikely to move a nanometre-grid coordinate or a three-decimal
G-code value; that expectation is an argument, not a measurement on this library, and C2 owns the
choice if R6 shows otherwise.

### What "the same output" rests on

The base FFF path is expected to be run-to-run byte-identical apart from the wall-clock line,
which is why L1 is the default gate rather than a tolerance. That expectation comes from informal
runs on a downloaded v2.5.2 binary during this intent's research — five runs of a cube, three of
the benchy, two of a third model — and nothing in this repository records them. R3 is what makes
it a fact: the base FFF row of `port/reports/determinism.md`, produced by R3's committed command
over at least five runs, is where the gate comes from, and R21 reads the level from that row
rather than asserting it here. If that row comes back weaker than L1, R21's gate moves with it.

The comparison order, once the port emits G-code, is: the statistics JSON first, because it is
per-layer, per-feature and per-object numbers that diff cleanly; then the G-code, which the
`; FEATURE:`, `; Z_HEIGHT:` and per-object label comments localise to a layer, a feature and an
object; then raw bytes. The statistics JSON is not an earlier signal than the G-code, because
both come from the same `GCodeProcessorResult`: it is the oracle's determinism instrument from
day one (R3) and becomes a port-vs-oracle surface at the same moment the G-code does. Its
`generator` field is a static version string the port cannot honestly reproduce, so R4 normalises
that one field.

R3 extends the measurement to the configurations nobody has measured — tree support, the wipe
tower, multi-filament, fuzzy skin. The per-configuration gate table in `docs/ORACLE.md` is
produced from that report, not authored here: where the oracle is not reproducible against
itself, no amount of fidelity reaches L1 and the gate is whichever weaker level the oracle reaches
against itself, or `none`. Three mechanisms are already known to make that so: a float reduction
over a concurrently filled vector feeding tree-support node geometry, a float sum over hash
iteration order in the wipe tower, and an entropy-seeded thread-local generator in fuzzy skin
(`src/libslic3r/Feature/FuzzySkin/FuzzySkin.cpp:38-44`). Fuzzy skin's generator is seeded per
thread from `std::random_device`, so its displaced points vary per run and per scheduling and no
R4 level is reachable for it, including L4's identical move count; its row's gate is `none` and
R27 reports it as a named divergence instead of failing.

Goldens are valid only for one platform: the mathematical library agrees bit for bit between Rust
and C++ here because both call the same system symbol, and the fused-multiply-add behaviour is
architecture-dependent. That is why R7 records the platform and R23 runs these checks on one.

### Scope, and why it is a manifest and not a list

Include analysis alone cannot scope this port in either direction. A headers-only closure reaches
149 files and 73,045 lines, which leaves out mandatory slicing code; three core files have no
header at all and no include edge reaches them; the model type drags in SLA, texture-baking and
project-format headers; and most of the library is reachable from the shipped binary. So scope is
computed by one script in the four passes R8 states, with the deductions named as reasons in
rows, and the result is a file a command regenerates and CI diffs. Everything downstream — plan
steps, tasks, progress, the port's own checks — reads that file. The same script carries a column
for coverage-measured execution during a benchy slice, populated when the local build exists;
that turns the include-reachability number from an upper bound into the measured subset, and it is
not a precondition for anything.

Equality tiers are a manifest column because the criterion is not uniform. The fixed-point parts
of the library — the wall generator, most of the infill, the algorithm and execution helpers, and
the files with no floating-point involvement — are held to exact equality of integer-coordinate
output. The float parts are held to the row's declared tolerance and comparison function, which
default to exact and loosen only with a reason in the row (R4). The G-code itself is held to a
level from R4.

### Order of work, and what the first comparison is

The include graph is acyclic at file granularity but is one 39-module cycle at the granularity
crate boundaries are drawn at, so the order of work is not derived from the graph — it is imposed
by R8's committed cut, and C10 owns that choice. The pipeline drivers sit at the top of the cut
graph, so a strictly bottom-up port produces no complete G-code until nearly all of the library
is ported, and no stage output at all until the pipeline steps themselves land: nothing printable
exists before the print-pipeline module, which is about two thirds of the way through by lines.

That is why R20 exists and why its gate is stated the way it is: the first comparison against the
vendored slicer is per-stage on the benchy, from the first *completed pipeline step* rather than
the first ported unit, and R21's end-to-end comparison is the acceptance gate rather than the
first output. Until the first pipeline step completes, R19's per-unit differential test against
the real C++ is the only proof the port has, which is the part of the trade-off C3 asks the
intent's author to confirm. No shim marshals the pipeline's shared mutable object graph across a
stage boundary in this intent: the boundary types are object graphs, not values, and that cost is
unmeasured.

### Faithful first, mechanically

Faithfulness is not a review sentiment here. It is: a contract written down before any unit is
ported (R12), with a command that checks the contract document exists and says what it must
(R29); a loop in which the implementer and both reviewers read the exact vendored source file the
module came from alongside the diff, and the reviewers are told to assume the module is wrong and
to cite `source:line` against `module:line` (R13), with the verdicts recorded on the unit's pull
request (R28); a trailer and marker set a script checks on every module (R14); a backlog that is
the only place a deferred optimization may live (R15); a burn-down of scaffolding to zero (R16);
a ban on substituting Rust libraries for the vendored and superbuild ones (R17); a differential
test against the real C++ for every unit, with a named proof path per file (R19); and a check that
every in-scope file was actually ported (R26).

The reference implementation is permanently available at a fixed path in the submodule, which is
what makes the sibling-source review possible at all. In the Bun port that sibling-file review was
one of four parity mechanisms, and the one its own research calls the pattern most worth copying
was a different one: a differential run against the shipped old binary. R3 to R6 are this port's
version of that mechanism, and R13's sibling-source review is the other.

## How each constraint in the intent is met

| Constraint | Met by |
|---|---|
| The pin of the vendored slicer remains as it is. | Nothing in this spec edits the vendored tree or moves the submodule pointer. The only changes to how the reference behaves are build flags, FFI against its own sources, and a test translation unit that `#include`s a vendored file without modifying it (R6, R17, R19), and every oracle output records the pinned commit (R7). The cost of that choice — that a few subsystems can then never be byte-matched — is C1. |

## Open questions from intent

### Q1: What is the exact workflow for porting, as per how the Bun Rust port worked?
- answer: answered

Answered from the Bun port's primary sources, checked against what this codebase allows. The
sources are: the account written by the engineer who ran it, <https://bun.com/blog/bun-in-rust>
(markdown at `bun-in-rust.md`); the merge commit `23427dbc12fdcff30c23a96a3d6a66d62fdc091d`,
"Rewrite Bun in Rust (#30412)", 2026-05-14, on <https://github.com/oven-sh/bun/pull/30412>; the
commit that carries `docs/PORTING.md` and the batch driver,
<https://github.com/oven-sh/bun/commit/46d3bc29f270fa881dd5730ef1549e88407701a5>; and the
v1.4.0 release post of 2026-08-20, <https://bun.com/blog/bun-v1.4>. Everything this spec takes
from that port is from one of those four.

The workflow is written into `docs/WORKFLOW.md` and `docs/PORTING.md` by R13 and R12: one source
file to one Rust module; a Phase A draft that need not compile, which is what makes wide
parallelism possible; Phase B compiling bottom-up with compiler errors as the work queue; one
implementer, two adversarial reviewers in separate contexts who read the sibling source and the
diff and cite both, one fixer; the markers and the `PORT STATUS` trailer; a banned-substitution
list the review stage rejects on; the conflict discipline for agents sharing a worktree; and a
three-unit trial before fan-out.

Four parts of that port do not transfer and are deliberately absent: its language-independent
test suite, which is why R3 to R6 build an oracle instead; its restructuring of its own source
tree, which the pin forbids and R8's manifest replaces; its single binary hosting both
implementations, for which no seam exists here; and its performance gates, which R15 excludes.
Its ownership-classification pass — a 2,253-row `docs/LIFETIMES.tsv` — does transfer in principle
and this spec does not adopt it: libslic3r states ownership in comments over raw pointers rather
than in types (`ExtrusionEntityCollection.hpp:39` `// we own these entities`, `:19`
`// Removed elements are NOT being deleted.`, `Model.hpp:189` `Model *m_model;` as a borrow, and
61 raw-pointer-container signatures in the headers), so the C++ analogue would be an ownership
manifest rather than a lifetime one. Whether that artifact belongs in this intent is C13, not a
decision taken here.

### Q2: What counts as "the same output" as the vendored slicer, and how is it compared?
- answer: answered

Answered by measurement on the pinned oracle and from upstream's own code. The levels, the
normalisation and the artifacts to compare are R4; the normalisation is exactly the four line
kinds upstream strips in `vendor/OrcaSlicer/tests/fff_print/test_slicing_pipeline_hook.cpp`; the
resolved-config JSON is compared with no normalisation and the statistics JSON with its static
`generator` field normalised. L1 — identical bytes after that normalisation — is the expected
gate for the base FFF path, and R3's report is what establishes it rather than this document. The
gate for every other configuration is produced by the same report, because where the oracle
cannot reproduce itself no port can match it; R27 holds the port to those gates; the subsystems
known to be in that position, and the port's deliberate divergences, are recorded by R18 and
carried as C1.

### Q3: What does OrcaSlicer currently call in the library?
- answer: answered

Answered from the vendored code. Both drivers — the application's headless path and the GUI's
background slicing process — call the same four entry points: `Model::read_from_file`,
`Print::apply`, `Print::process` and `Print::export_gcode`. Scope is computed from those in the
four passes R8 states, with named deductions, and kept current by R8's manifest; SLA is excluded
by file rather than by directory (R9). Four consequences are design decisions rather than open
questions: command-line option parsing belongs to the library and not to application code, so it
is in scope; the plate layer that supplies bed shape and wipe-tower placement lives in the GUI
library, so it is out of scope and the port takes resolved configuration instead (R10, R11); the
Bambu-printer flag is set explicitly by the caller because validation depends on it; and
`GCode/GCodeStatistics` is in scope because the application calls it, even though it runs after
`Print::export_gcode` returns. Three groups the application does reach are nonetheless deducted —
arrange and orient, the project-format readers, and the preset layer — and each deduction carries
its reason in R8 and a concern (C14, C6).

## Areas of concern

### C1: Byte parity for some subsystems requires changing the oracle, which the pin forbids
- owner: Bruk Habtu

The intent asks for the same output as the vendored slicer, and for the pin to remain as it is,
with the old library as the oracle. For tree support, the wipe tower and fuzzy skin these cannot
both hold: the vendored slicer is not reproducible against itself there — a float reduction over
a concurrently filled vector feeds tree-support geometry, a float sum runs over hash iteration
order in the wipe tower, and fuzzy skin is seeded from entropy per thread — so no Rust port can
reach L1 against it, and reaching byte parity would mean patching the reference to be
deterministic, at which point the baseline stops being the old library.

This spec takes the side of the pin: build flags and FFI only, the Rust port made deterministic,
and the divergence named and checked at a looser level (R18, R27, and the gate table from R3).
The proposal to the owner is to accept that, with the alternative being an explicitly reviewed
determinism overlay on the oracle for those subsystems, recorded in `vendor/README.md` and
treated like a pin move. R3 tells us how much is actually at stake before anyone decides.

**Decision (2026-11-24).** Decided by Claude (Fable), acting for Bruk Habtu, who handed over this intent's decisions and merges before stepping away. Accepted as proposed: the pin holds, the oracle is not patched, the port is deterministic, and each divergence is named in `port/reports/divergences.md` and checked at the gate R3 measures. No determinism overlay is built in this intent.

### C2: The two oracles may disagree, and then one of them is not "the old library"
- owner: Bruk Habtu

The released binary is built as shipped; the local build adds `-ffp-contract=off` so the
reference matches Rust's arithmetic semantics and stops being architecture-dependent. Both are
built from the pinned commit, and the difference is very unlikely to reach a printed coordinate,
but that is an argument and it is unmeasured for this library. R6 measures it. If the two disagree
materially, the owner decides which is normative — the binary a user would actually run, or the
build the port can match — and whether goldens are then per-oracle. The same choice fixes the
platform: these goldens are valid for one operating system and architecture only.

**Decision (2026-11-24).** Decided by Claude (Fable), acting for Bruk Habtu, who handed over this intent's decisions and merges before stepping away. The locally built library with `-ffp-contract=off` is the normative oracle for every per-unit and per-stage proof, and macOS arm64 is the one platform goldens are valid for. For the end-to-end gates (R21, R22, R27) the pinned release binary is normative where R6 shows the two agree at L1. Where R6 shows they disagree, the built oracle is normative for that fixture and configuration, the disagreement is a named row in `port/reports/divergences.md`, and goldens are kept per oracle.

### C3: "A benchy as a first output" and a bottom-up port pull against each other
- owner: Bruk Habtu

The intent names slicing a benchy and comparing the results as the first output. The library's
pipeline drivers sit at the top of its dependency graph, so an end-to-end G-code comparison
through the port is only possible once nearly all of the library is ported. This spec reads "first
output" as the first comparison and makes it per-stage on the benchy (R20), with the end-to-end
comparison as the acceptance gate (R21). The owner should know what that buys: a per-stage
comparison starts at the first *completed pipeline step*, not the first ported unit, and nothing
printable exists before the print-pipeline module, about two thirds of the way through the library
by lines. Until then R19's per-unit differential test against the real C++ is the only proof the
port has. The alternative is a throwaway bridge that serves unported stages from the vendored
C++, which would make a mixed end-to-end slice possible much earlier; its cost is unmeasured, and
the boundary marshals a shared mutable object graph rather than values. The owner decides whether
the per-stage reading is the one they meant, knowing it is not an early end-to-end signal.

**Decision (2026-11-24).** Decided by Claude (Fable), acting for Bruk Habtu, who handed over this intent's decisions and merges before stepping away. The per-stage reading is accepted: the first comparison is per stage on the benchy (R20) and the end-to-end comparison is the acceptance gate (R21). No throwaway bridge to the vendored C++ is built.

### C4: At the end of this intent the port still links C and C++
- owner: Bruk Habtu

R17 binds the vendored Clipper2 — which the vendored copy patches in two behaviour-changing ways
that no published crate carries — along with admesh, libnest2d and qhull from `deps_src/`, and
Boost.Polygon's Voronoi builder and possibly NLopt from the `deps/` superbuild, which have no
vendored source and are fetched by the pin's own recipes. That is the only way to be exact by
construction, and it keeps those diffs out of the way while the library itself is validated. It
also means "the slicer lib is ported to Rust" is true of libslic3r and not of everything it links,
and that two of the six are pinned by a recipe rather than by the submodule. The proposal is to
accept it for this intent and let a later intent replace each one, validated against the FFI
build.

**Decision (2026-11-24).** Decided by Claude (Fable), acting for Bruk Habtu, who handed over this intent's decisions and merges before stepping away. Accepted for this intent. Replacing the linked C and C++ libraries is left to a later intent.

### C5: Equality of G-code is necessary and not sufficient
- owner: Bruk Habtu

A faithful translation of C++ pointer discipline reaches for `unsafe`, and the compiler is
entitled to assume away what the original did by convention. In the Bun port, undefined behaviour
reachable from ordinary safe code was found by an outsider hours after a green suite merged
(<https://github.com/oven-sh/bun/issues/30719>, filed 2026-05-14, the day of the merge; the blog
at <https://bun.com/blog/bun-in-rust> is where the suite's assertion count and the nineteen
regressions it later acknowledges come from). This spec requires a `// SAFETY:` comment on every
`unsafe` block (R14) and nothing more; sanitizers, Miri and fuzzing beyond R19's differential
targets are not requirements here. The owner decides whether that belongs in this intent or the
next.

**Decision (2026-11-24).** Decided by Claude (Fable), acting for Bruk Habtu, who handed over this intent's decisions and merges before stepping away. This intent requires the `// SAFETY:` comment (R14) and R19's differential fuzz targets and nothing more. Sanitizers and Miri are left to the following intent, which is the one that changes the code's shape.

### C6: 3MF project files and presets are out of scope, that is how Bambu users work, and the print is the owner's call
- owner: Bruk Habtu

R11 takes resolved configuration as the port's input and R8 deducts the project-format and preset
layers, which is what keeps a benchy difference attributable to slicing, and which are by far the
largest files in that layer (`Format/bbs_3mf.cpp` 10,211 lines, `PresetBundle.cpp` 9,351,
`Preset.cpp` 5,266). The consequence is that at the end of this intent the port slices a mesh
plus a resolved config, not a 3MF project from the slicer's own workflow. R22 is the measurable
half of the intent's "usable to slice files for 3D printing": the port's G-code equals the
oracle's on every committed fixture. The other half is the owner's own acceptance — printing the
port's benchy G-code on a Bambu X1 Carbon — which is deliberately not a requirement, because
where R22 holds the port's G-code is identical to the oracle's and the print says the same about
both. The owner decides whether R22 plus their own print is enough without the project-format and
preset layers, or whether either belongs in this intent.

**Decision (2026-11-24).** Decided by Claude (Fable), acting for Bruk Habtu, who handed over this intent's decisions and merges before stepping away. R22 is accepted as the measure of "usable to slice files for 3D printing" for this intent: the port slices a mesh plus a resolved configuration. The project-format and preset layers stay out, and the print on an X1 Carbon stays the owner's own act and is not a requirement.

### C7: The fine oracle depends on a build nobody has exercised on this platform
- owner: Bruk Habtu

Building the library with the GUI off is supported by the upstream CMake logic and used by one
upstream script, `scripts/CAD/run-kernel-tests.sh`, but only inside a Linux docker image, only
for one test target, and never on macOS: no upstream workflow sets it, and upstream's own comment
on that script argues the combination is sound rather than untested. The caveat that nobody has
built it on macOS is recorded in grampus's `vendor/README.md`, not upstream. The dependency
superbuild also still requires most of the heavy libraries with the GUI off, and no part of it is
prebuilt here. If that build cannot be made to work, R5, R6, R19 and R20 lose their per-stage
oracle and the only comparison left is end-to-end, which cannot localise a divergence to a stage —
and R19's first and third proof paths both go through it, so no single ported unit can be proven
until it works. The proposal is to attempt it early, as its own piece of work, and to report back
rather than work around it.

**Decision (2026-11-24).** Decided by Claude (Fable), acting for Bruk Habtu, who handed over this intent's decisions and merges before stepping away. Accepted as proposed: the build is attempted first, as its own piece of work, and no port unit is started before it works. If it cannot be made to work, that is reported and the work that depends on it stops; it is not worked around.

### C8: The size of this intent is not a schedule, and nothing here makes it smaller
- owner: Bruk Habtu

Scope is around 245,000 lines across roughly 420 files, before any deduction a coverage run might
justify. The comparison the intent invites is the Bun port, and its own published account
(<https://bun.com/blog/bun-in-rust>, with the v1.4.0 release post of 2026-08-20 at
<https://bun.com/blog/bun-v1.4>) reports about $165,000 of model time at API pricing, eleven days
from start to merge and about three and a half months to a stable release, nineteen acknowledged
regressions, and a green suite that still had undefined behaviour in it (C5). Those are that
project's self-reported figures on a larger but far easier language pair, not an estimate for this
one, and no third-party replication of them was found. This spec is written so the work can
proceed and be checked piece by piece, and so that no single piece has to be finished for the rest
to be verifiable; it does not shorten the work. The owner should know that before the plan is cut.

**Decision (2026-11-24).** Decided by Claude (Fable), acting for Bruk Habtu, who handed over this intent's decisions and merges before stepping away. Noted. The work proceeds piece by piece as this spec describes, and the size is not reduced.

### C9: SLA is excluded, but the slicing pipeline calls part of it
- owner: Bruk Habtu

The intent says twice that SLA is out, and also says what is ported is what OrcaSlicer calls in
the library. For `SLA/IndexedMesh` those pull against each other: it is a generic raycast and
AABB structure, and Z-contouring calls it from `ContourZ.cpp`, with `AABBMesh.cpp`,
`PrintObject.cpp` and `Layer.hpp` in the same closure. Excluding it by its directory name would

### C10: The crate-level cut is a design choice nobody has made yet
- owner: Bruk Habtu

The include graph is acyclic at file granularity, but crate boundaries are drawn over modules and
at that granularity it is one cycle: 5 components for 43 modules, one holding 39 modules and
321,722 of 337,335 lines. Rust crates cannot depend on each other circularly, so a cut is
mandatory. A 62-edge feedback arc set carrying 156 of 2,696 include references makes the graph
acyclic, and most of those edges are stray single includes that are cheap to cut, but which
62 edges get cut decides the crate map and therefore the whole order of work. Two pairs are
genuinely mutual and cannot be cut at all: `GCode.cpp` with `GCode/*` and `Model` with `Format`.

The proposal is that R8's script computes the cut, commits it as `port/cut.tsv`, and derives every
level from the cut graph, so the order of work is reproducible rather than asserted, and that the
two mutual pairs are single crates. The owner decides whether a 62-edge cut chosen by a greedy
algorithm is acceptable as the crate map, or whether the crate boundaries should be designed by
hand first.

**Decision (2026-11-24).** Decided by Claude (Fable), acting for Bruk Habtu, who handed over this intent's decisions and merges before stepping away. The computed cut is accepted as the crate map, committed as `port/cut.tsv`, with `GCode.cpp` and `GCode/*` as one crate and `Model` and `Format` as one crate. The cut is reviewed like any other change in the pull request that commits it, and is changed afterwards only by a pull request that regenerates the manifest.

### C11: The per-stage oracle cannot see inside G-code export
- owner: Bruk Habtu

`SlicingPipelineStepPlugin` has no value for `psGCodeExport` or `psConflictCheck`, and none for
`posSimplifySupportPath`, `posSimplifyWall` or `posSimplifyInfill`. Its one G-code-related value
fires from the GUI, after the file is written, and R10 puts that layer out of scope. So the stage
oracle that R5, R19 and R20 rest on stops at `psSkirtBrim`, and a divergence anywhere in the
largest in-scope subsystem — the G-code modules, tens of thousands of lines, and the one that
produces the artifact R21 and R22 compare — can be detected but not localised to a stage.

R20's stated fallback is the comparison the design already describes: R4's levels on the exported
G-code, localised by the `; FEATURE:`, `; Z_HEIGHT:` and per-object label comments, and the
command says it is in fallback rather than naming the last seam as the first difference. The
proposal is to accept that for this intent. The alternative is to dump the extrusion-entity tree
or the `GCodeProcessorResult` at `psSkirtBrim` and compare that as a pseudo-stage, which would
split the gap in two without touching the vendored tree; its cost is unmeasured. The owner decides
whether the fallback is enough.

**Decision (2026-11-24).** Decided by Claude (Fable), acting for Bruk Habtu, who handed over this intent's decisions and merges before stepping away. The fallback is accepted for this intent. A pseudo-stage dump at `psSkirtBrim` is not required.

### C13: An ownership manifest may belong in this intent
- owner: Bruk Habtu

One of the five things this intent's research names as worth taking from the Bun port is its
lifetime-classification pass: a committed table, one row per field, classified and adversarially
verified before any unit was ported. The C++ analogue is an ownership manifest — per raw pointer field and parameter,
whether the holder owns, borrows or copies, with a cited evidence line. libslic3r needs it more
than the spec's first draft assumed: ownership there is stated in comments over raw pointers
(`ExtrusionEntityCollection.hpp:39` `// we own these entities`, `:19`
`// Removed elements are NOT being deleted.`) rather than in types, and the headers carry 61
raw-pointer-container signatures.

This spec does not require that artifact, because the intent does not ask for it and it is a
substantial piece of work in its own right — a table over the raw-pointer surface of about 420
in-scope files, verified before fan-out. The proposal is to decide it now rather than discover it
mid-port: either add it as a requirement in this intent, so the manifest is committed and binding
on porters before Phase A, or leave R12's don't-translate list and R14's `// SAFETY:` rule to
carry the risk and let the following intent build it. The owner decides.

**Decision (2026-11-24).** Decided by Claude (Fable), acting for Bruk Habtu, who handed over this intent's decisions and merges before stepping away. The ownership manifest is brought into this intent, as R30, because the requester asked for the approach the Bun port took and this pass is one that port did before any unit was ported.

### C14: Arrange and orient are deducted from scope although the application calls them
- owner: Bruk Habtu

The intent's scope rule is that what is ported is what OrcaSlicer currently calls in the library,
and OrcaSlicer does call libslic3r's arranger: from the CLI's `--copy` handler
(`src/OrcaSlicer.cpp:5040`), from the GUI (`Plater.cpp`, `Jobs/ArrangeJob.cpp`,
`Jobs/FillBedJob.cpp`), and from the test harness R10 names its surface
(`tests/fff_print/test_helpers.cpp:277`). `Arrange.cpp`, `ModelArrange.cpp`, `IMEXArrange.cpp`
and `Orient.cpp` are all libslic3r files. R8 deducts them anyway.

The reason is that the CLI's default arrange path runs through `Slic3r::GUI::PartPlate`, which
R10 already puts out of scope, and that R24 fixes placement in the fixture and passes
`--arrange 0`, so no arranger runs on either side of any comparison — which makes porting it
unprovable by any oracle this spec builds. The proposal is to accept the deduction and let the
following intent port arrange against a GUI-side oracle. The alternative is to bring arrange into
scope now and prove it against the test harness's `arrange_objects(model, InfiniteBed{}, ...)`
call rather than against the CLI, which is a narrower oracle than everything else here uses. The
owner decides.

**Decision (2026-11-24).** Decided by Claude (Fable), acting for Bruk Habtu, who handed over this intent's decisions and merges before stepping away. The deduction is accepted. Arrange and orient are left to the following intent.
